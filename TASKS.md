## 3. Transfer production database (strategy, to be decided)

Problem: production runs the old `main` schema (migrations `events` up to 0173,
`shop` 0021), the new code has reset migrations (`events` 0001-0034, `shop` 0001)
and changed models (moodle fields removed, `check` -> `agree`, ...). The migration
histories don't connect, so `migrate` cannot upgrade the production DB in place.

Proposed way (rehearse on einstein until it runs clean, then script it):

1. Export from production with the **old** code:
   `dumpdata --natural-foreign --natural-primary -e contenttypes -e auth.permission
   -e admin.logentry -e sessions --indent 2 > prod.json`
2. Transform `prod.json` with a script (cf. `prepare_data.py`): drop removed fields,
   rename changed ones, map models that were split/merged. Diff old vs new
   `models.py` to get the list.
3. Fresh Postgres on einstein, `migrate` with the new code, then `loaddata prod.json`
   and `sqlsequencereset <apps> | dbshell`.
4. Copy media: public dirs -> `data/media/`, private dirs (`invoices/`, `confirmations/`,
   `uploaded_private_documents/`, `stornos/`) -> `data/private/` (file paths in the DB
   stay the same, only the storage root changes).
5. Take over `SECRET_KEY` and `ENCRYPT_KEY` from production (newsletter tokens,
   sessions) instead of the generated ones.

Open questions:
- Which DB engine does production use (SQLite / MySQL / Postgres)? If SQLite, `pgloader`
  is an alternative to dumpdata/loaddata for the raw copy.
- How is mail sending triggered on production today (cron `send_queued_messages`?) -
  container setup assumes the queue is used.
- Production `local_settings.py` values (PayPal, member admin API URLs, ...) to copy into
  host_vars.
